PQ-FORENSIC · SIH PS 26237

How the system catches a leaker

A walkthrough for anyone who can read code but hasn't met post-quantum crypto, forensic watermarking, or Merkle trees. Every mechanism names the technology that implements it.

01The problem in one picture

A commander encrypts one report and sends it to five officers. Each decrypts it with their own key. Days later the report appears on a messaging app.

Who leaked it? Every officer decrypted the same file and got back byte-for-byte identical plaintext. Nothing in the leaked copy points at anyone.

Why the obvious fixes fail

Server access logs? An administrator with database access can edit them. The evidence sits in exactly the place a privileged insider controls.

A watermark stamped before sending? Every recipient gets the same mark — which reproduces the same problem it was meant to solve.

02The core idea

Move the watermark from before distribution to the moment of decryption. Each recipient's software marks the file as it is decrypted, so every copy looks identical but carries a different hidden pattern.

03How an invisible mark fits in a PDF

The mark hides in the spacing between words. Each bit nudges one gap slightly wider and the next one narrower by the same amount.

Why a pair of gaps, not a single one

We measured real PDFs first. In justified text, word gaps naturally vary with a standard deviation of 0.77pt — more than twice the 0.35pt signal we can hide invisibly. Encoding a bit in one gap's absolute width is unrecoverable; the natural variation drowns it.

Comparing two neighbouring gaps cancels that out: justification stretches the whole line roughly equally, so it affects both gaps and vanishes from the difference.

04What happens when someone decrypts

Decryption isn't a passive read. Six things happen, in this order, and the order matters.

  1. Unwrap the content key The file was encrypted once under a random key. That key was sealed separately for each recipient, so only their private key opens their copy. ML-KEM-768 (FIPS 203) · crypto/kem.py
  2. Decrypt the document Standard symmetric decryption. The authentication tag also proves the file wasn't altered in transit. AES-256-GCM · crypto/aead.py
  3. Generate this session's mark A fresh random seed produces a codeword unique to this recipient and this decryption. Decrypting twice gives two different marks. Tardos fingerprinting · watermark/tardos.py
  4. Embed it in the spacing Word gaps are nudged as shown above. The reader sees no difference. PyMuPDF · watermark/spacing.py
  5. The recipient signs the record A note saying who / which document / which mark / when, signed with the recipient's own private key. They cannot later deny it. ML-DSA-65 (FIPS 204) · crypto/sig.py
  6. Commit to the ledger The signed record is appended to a tamper-evident log and an inclusion proof comes back. RFC 6962 Merkle tree · ledger/node.py

05Why an administrator can't rewrite the log

The audit log is a Merkle tree. Every record is hashed, pairs of hashes are hashed together, and so on up to a single root hash that is signed.

To hide an edit, an administrator would have to forge the signature over the new root. That needs the node's private key. And to fully cover the tracks they would also need to forge the recipient's signature on the record — a different key again, held by someone else entirely.

“Why not a real blockchain?”

Blockchains solve consensus among strangers — who gets to write next when nobody trusts anybody. Here every participant already holds a strong cryptographic identity and the group is known in advance, so that problem doesn't exist.

What's actually needed is append-only proof: evidence the log has only grown and never been rewritten. That's what Certificate Transparency does for the web's certificate system, and it's a fraction of the machinery.

Why "post-quantum" at all

A large quantum computer would break RSA and elliptic-curve cryptography. Nobody has one yet — but classified documents stay sensitive for decades, and an adversary can record encrypted traffic today and decrypt it later. The algorithms here were standardised by NIST in August 2024 for exactly that reason.

08What it does not do

Worth knowing before anyone asks.

LimitWhy
A screenshot or photo can't be traced The mark lives in the text layer's geometry. Turning the page into pixels destroys it.
A skilled recipient could patch the software The marking runs on their machine. Truly preventing this needs hardware support (a TPM or secure enclave). But a leaked file with no valid mark is itself suspicious — the ledger still records who could decrypt.
Signatures prove a key was used, not that a person intended it That's true of all digital signatures. Non-repudiation rests on the duty to protect your key, not on mathematics.
Very short documents are refused A mark needs room. Rather than half-mark a file it couldn't defend, the system rejects it with a clear message.

Glossary

KEM (Key Encapsulation Mechanism)
A way to send a secret key to someone using only their public key. ML-KEM-768 is the post-quantum one.
Digital signature
A value only the holder of a private key could produce, which anyone can check with the matching public key.
Hash
A short fingerprint of some data. Change one byte and the fingerprint changes completely.
Merkle tree
Hashes of hashes, arranged in a tree. Lets you prove one record is in a large log without sending the whole log.
Inclusion proof
The handful of hashes needed to show a record really sits in the tree under a given root.
Collusion
Two or more recipients comparing copies to find and remove the mark.
Air-gapped
A machine with no network connection at all. Everything here works that way.
